# Frontend contributor instructions

This file extends the repository-level `AGENTS.md` for everything under
`frontend-src/`.

## Non-negotiable UI contract

- Build the panel with standard Home Assistant UI components and interaction patterns.
  Reuse the components Home Assistant uses on its own settings pages.
- Do not introduce raw `button`, `select`, `textarea`, or `table` controls, a
  custom replacement for an existing Home Assistant component, or a separate UI
  framework. Use components such as `ha-button`, `ha-icon-button`,
  `ha-textfield`, `ha-select`, `ha-switch`, `ha-card`, `ha-alert`,
  `ha-dialog`, selectors, and `hass-tabs-subpage-data-table` as appropriate.
- Use Home Assistant icons, typography, spacing, color variables, dialogs, more-info
  behavior, and navigation. Do not hard-code theme colors that have a semantic Home
  Assistant CSS variable.
- Preserve desktop, mobile, keyboard, and screen-reader usability. Controls need a
  visible label or accessible name; icon-only actions need a tooltip.
- Keep tables consistent with Home Assistant: shared search, filters, sorting, column
  visibility, selection, grouping, and responsive primary/secondary information.
- Keep all user-visible strings in the translation flow. Update both French and
  English translations for every new label, error, status, or help text.

## Source architecture

| Path | Responsibility |
| --- | --- |
| `alert-manager-panel.js` | Custom-element lifecycle, global state, subscriptions, routing, and explicit orchestration only. |
| `api/alert-manager-api.js` | The only direct `hass.callWS` boundary, plus loading and refresh coordination. |
| `views/*.js` | One tab's markup, actions, hydration, and targeted refreshes. |
| `components/alert-table.js` | Shared alert/history table behavior and Home Assistant data-table integration. |
| `components/rule-editor.js` | Rule drawer, visual/YAML editors, validation display, and draft handling. |
| `utils/escaping.js` | HTML escaping for dynamic markup. |
| `utils/formatting.js` | Display-only formatting and rule summaries. |
| `utils/translations.js` | Translation loading, lookup, and error localization. |
| `utils/table-preferences.js` | Namespaced, bounded table preference persistence. |
| `utils/constants.js` | Shared frontend constants and icon mappings. |
| `styles/*.js` | Styles split by responsibility; `panel-styles.js` only combines them in cascade order. |

`custom_components/alert_manager/frontend/alert-manager-panel.js` is generated by
`npm run build`. Never edit or patch the generated bundle. If a source module is
added, register it in the deterministic order used by both the build and frontend
lint scripts, and avoid top-level identifier collisions in the standalone bundle.

## State and rendering

- Keep WebSocket message construction and direct calls in the API module. Views and
  components call the panel's API helpers; they do not create a second transport path.
- Keep tab-specific behavior in its view. Keep genuinely shared table/editor behavior
  in components and pure reusable transformations in utils.
- Prefer targeted DOM/data-table updates when data, busy state, notices, or countdowns
  change. Reserve a full panel render for structural changes such as navigation,
  loading, or opening/closing an editor.
- Use explicit imports and composition. Do not mutate prototypes, install runtime
  mixins, or transform generated markup with fragile string replacement.
- Reuse the shared action delegation and hydration paths. Do not attach untracked
  duplicate listeners after every render.
- Escape dynamic content with the shared escaping helper before inserting it into
  template markup. Prefer DOM properties/events where practical; never use `eval`,
  `new Function`, cookies, or unsafe HTML from backend/user data.
- Keep browser storage limited to the existing namespaced table preferences. Runtime
  and configuration state belong to Home Assistant/backend storage.
- Keep styles in the responsibility-specific style module, indented and readable.
  Preserve the aggregator's cascade order and centralize compact mobile rules in the
  responsive stylesheet.
- Avoid frontend dependencies unless the task clearly cannot use Home Assistant's
  built-in platform. A small focused helper is preferred over copied markup or logic.

## De-duplication rules

Before adding code, search `views/`, `components/`, and `utils/` for the same
behavior. Extend the shared implementation when semantics match:

- table mechanics belong in `components/alert-table.js`, not independently in views;
- rule form mechanics belong in `components/rule-editor.js`;
- display formatting, escaping, translations, constants, and preferences each have one
  authoritative utility module;
- view modules contain only differences specific to their tab.

Do not force unrelated behavior through a generic helper merely to reduce line count.
A shared abstraction must have a clear name, stable inputs/outputs, and at least two
real consumers.

## Validation

Use Node.js 20 or newer. For every frontend change, run:

```sh
npm run build
npm run lint:frontend
npm run test:frontend
```

Commit the regenerated standalone bundle with its source changes. Verify that a fresh
build produces no additional bundle diff. Add or update a focused Node regression test
for changed behavior, and run the Python suite too when the WebSocket contract or
backend-facing data shape changes.
